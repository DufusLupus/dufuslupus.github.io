FEATURED PROJECT

Particle LifeSimulation

A particle simulation that runs in the browser. Different particle types attract or repel each other according to a set of rules.

I designed and built it independently using TypeScript. Web Workers handle the simulation, and Pixi.js draws the particles.

  • TypeScript
  • Web Workers
  • SharedArrayBuffer
  • Pixi.js

HOW IT STARTED

I saw a video and thought
I could build it.

I saw a YouTube video of a particle-life simulation and thought: hey, maybe I can make this too.

Then I wondered how far I could push it — what happens if I try to run silly particle counts in a browser?

I used TypeScript mostly because it was the language I’d used most recently, and because my previous experience building GUIs in Python had been a pain.

HOW IT EVOLVED

CPU FIRST / GPU NEXT

I deliberately built the simulation in stages. I didn’t know what the final architecture would look like — I wanted to make something work, find out what stopped working, and then solve that problem.

  1. 01

    Inline brute force

    Everything in one file, with a nested loop comparing every particle with every other particle. On my machine, performance became a problem at roughly a few hundred particles, depending on settings.

  2. 02

    Separate simulation & rendering

    Split the simulation, rules and rendering into their own components.

  3. 03

    Spatial grid

    Narrow the neighbour search. That got me further, but I was still compute-bound.

  4. 04

    Modular architecture

    Give simulation, rendering and spatial lookup their own boundaries.

  5. 05

    Runtime controls

    Keep rules and other parameters changeable while the simulation runs.

  6. 06

    Shared memory

    Put particle state in typed arrays backed by SharedArrayBuffer.

  7. 07

    Web Workers + Atomics

    Divide the particles into slices and coordinate each frame.

  8. 08

    Testing & benchmarking

    Compare partitioners, use seeded inputs and revisit the timing tools.

  9. NEXT

    GPU

    Try moving the simulation to WebGPU.

The broad progression. Some of these overlapped, and I’ve come back to them as the code changed.

Around the same time I kept breaking the project into more independent pieces. Eventually I wanted the simulation itself not to care how things like spatial lookup were implemented.

Spatial partitioning now sits behind a common interface and module registry. The simulation can select a different spatial implementation by name without the rest of the engine needing to know how it works.

That design has already become useful: I’ve built a brute-force implementation behind the same interface, so I can use the simple version as a reference when testing the optimised spatial algorithms.

GETTING IT PARALLEL

Sharing the work
between workers.

Once spatial lookup wasn’t the only bottleneck anymore, I started looking into what parallelisation JavaScript actually offered. That led me to Web Workers, then SharedArrayBuffer, and eventually Atomics.

I didn’t start with a plan to build a shared-memory worker architecture. I got there through a lot of trial and error.

There were problems at pretty much every step: constructing and tearing down the worker pool, dividing particles between workers, sharing buffers safely, signalling the start and completion of frames, swapping position buffers, and building a force module that each worker could use independently for its own slice of particles.

That’s probably the part of the project I’m most pleased with. It went from “JavaScript has Web Workers” to multiple workers cooperating on the same simulation state without copying all of that state around every frame. I also built the synchronisation boundaries with Atomics, so scripts that otherwise don’t know about each other can coordinate when a frame starts and when it’s finished.

On my machine, the current CPU version can handle roughly 10,000 particles depending on the settings.

THE CURRENT ENGINE

IMPLEMENTATION

How the simulation
works.

The grid handles neighbour lookup, workers calculate the next frame, and Pixi.js draws the result. Keeping those parts separate makes it easier to change one without rewriting the others.

01 / CONCURRENCY

Workers and shared memory

A worker pool divides particles into slices. Float64Array and Uint8Array views over SharedArrayBuffer hold simulation state; Atomics signals each frame and tracks worker completion.

02 / DATA ORGANISATION

Neighbour lookup

A uniform grid groups particle indices into contiguous cell ranges. Radius-based queries visit candidate cells instead of scanning every particle for every interaction.

03 / REPRODUCIBILITY

Seeded initialisation

I use a seeded Mulberry32 generator for rules, positions and particle types, and a fixed simulation step. That gives me a consistent starting point when I’m comparing changes.

FRAME UPDATE

From simulation to rendering

The main thread prepares the grid and frame parameters. Workers read one position buffer and write the next. Rendering receives the completed positions only after the workers finish.

RENDERING

Drawing the particles

Pixi.js ParticleContainer uses a shared particle texture, additive blending and dynamic positions. Renderer.sync() copies completed simulation positions into render particles.

SHARED STATE

Reading one frame, writing the next

Positions, velocities and force accumulators use Float64Array views over shared memory. Each worker reads the same position buffer and writes a separate particle slice into the next one, so it doesn’t overwrite positions another worker still needs.

CHANGING THINGS WHILE IT RUNS

The settings are part
of the simulation.

One thing that has made the project harder is that I really wanted the simulation to stay interactive.

Almost everything except things like particle count and world size can change while it’s running. Interaction rules, radii, repulsion behaviour, friction, speed, force limits and boundary behaviour can all change from frame to frame.

That meant I couldn’t optimise around the assumption that the simulation configuration would stay fixed after startup.

The runtime parameters have to make their way through the simulation and shared worker state while everything keeps running.

It made parts of the architecture more complicated, but being able to change the rules and immediately see different behaviour is also one of the things I like most about the project.

WHAT I GOT WRONG

Pretty much everything
at some point.

That’s partly how I wanted to build it. Instead of trying to predict the final design, I kept replacing things once I understood why they were becoming a problem.

Benchmarking is actually one of the things I’m rebuilding now.

The first benchmarking system became too specific to the version of the simulation it was written for. As the architecture changed, keeping it working became increasingly awkward, and eventually the project moved on without it.

I’d rather rebuild that around the current modular architecture so benchmarks are easy to run and useful while the implementation keeps changing, instead of having another benchmarking system that’s tightly coupled to one version of the engine.

I’ll add benchmark results once the rebuilt system is working.

WHAT’S NEXT

Still a work
in progress.

The project isn’t finished. Most parts are still actively changing.

The main things I’m working towards now are:

  • Better automated testing, including comparing optimised implementations against simpler reference implementations.
  • Rebuilding the benchmarking system.
  • Finishing the runtime UI.
  • A movable camera and viewport.
  • Moving the simulation onto GPU compute shaders.

The GPU version is the part I’m most curious about because it’s completely new territory for me.

After that I might try implementing the same simulation in a more performance-focused language and see how much of the limitation is the browser and JavaScript, and how much comes from the algorithms themselves.
